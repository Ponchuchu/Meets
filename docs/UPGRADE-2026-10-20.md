## Порядок следующих выпусков

Первая проверяемая гипотеза: `1701723` читает `map_frame/map_trail` и вызывает `my_chat_summaries`, добавленные миграцией **27**, а сохранённый отчёт обновления сервера относится к миграциям **25–26**. Если 27 не применена, списки друзей/чатов могут не загрузиться, а прежний индикатор ошибочно называет это отсутствием связи. Это установлено сравнением исходников и отчётов; состояние живой базы пока неизвестно. Безопасная проверка: `npm run diagnose:backend` (только чтение, вывод без ключей и личных данных). При запрете сети или отсутствии авторизации результат нельзя трактовать как отсутствие таблиц.

### 1. Надёжное основание — приоритет P0

- Сверить установленную сборку с коммитом и получить логи сбоя, время и идентификатор запроса. Разделить DNS/TLS, REST, Auth, Realtime и Storage.
- Снять резервную копию базы и проверить восстановление на отдельном проекте. Затем применить миграцию на стенде и выполнить сценарий двух аккаунтов.
- Разнести весь локальный кэш, социальные флаги, рекомендации и черновики по аккаунтам. Очередь уже проверяет владельца, но полная изоляция всех остальных хранилищ ещё не реализована.
- Проверить RLS всех таблиц, приватных бакетов, групп, приглашений, блокировок и геолокации. Новые SQL-проверки покрывают выбранные исправления, а не весь Supabase.
- Подключить отмену HTTP-запросов через AbortSignal; сохранять в журнале безопасный request ID и причину ошибки. Отдельно показывать «Нужно войти снова», «Не удалось обновить» и отсутствие интернета.
- Уточнить права редактирования/скрытия сообщений: изменение чужих сообщений закрыто, «скрыть у себя» следует делать отдельным RPC.
- Ограничить фоновые подписки и опросы временем активности приложения; добавить восстановление после долгого сна и смены сети.

Готово, когда: на двух устройствах дружба и чат переживают перезапуск; отправка при потерянном ответе даёт одно сообщение; выход/вход другим аккаунтом не показывает чужих данных; доступ к чужому чату запрещён.

### 2. Чаты и медиа — P0/P1

- Проверить существующую пагинацию `(created_at, id)` и виртуализованный список на длинной истории, удалениях и сохранении позиции.
- Проверить существующий `my_chat_summaries` на большом аккаунте и актуальность миграции 27 на сервере; измерить EXPLAIN ANALYZE.
- Статусы «готовится → отправляется → доставлено / повторить», отмена проблемного вложения и отдельная очередь на каждый чат. Один плохой файл не должен задерживать другие диалоги.
- Копировать исходники ожидающих отправки в устойчивое хранилище приложения; очищать после подтверждения. На web Blob URL не переживает перезапуск страницы.
- Для всех платформ: серверное перекодирование видео в H.264/AAC, 720p для кружков и 1080p для обычного видео, ограничение частоты кадров и битрейта. H.264/AAC проверять на реальных устройствах; имя формата само по себе не гарантирует плавность.
- Превью фото 320/720/1080, постеры видео, потоковое воспроизведение с Range, ограниченный кэш и обновление подписанных ссылок. Сейчас ссылки действуют час.
- Ограничение размера/длительности перед загрузкой, прогресс и возобновление больших загрузок. Проверять MIME; не хранить весь большой файл в JS ArrayBuffer.
- Обрабатывать отказ камеры/микрофона, прерывание звонком, отсутствие места, запись меньше секунды и смену приложения во время записи.

Готово, когда: чат с 1000 сообщений и вложениями не создаёт 1000 плееров; воспроизводится один ролик; фото правильно повёрнуто; 4K-исходник действительно перекодируется, а повтор не удваивает файл/сообщение.

### 3. Рекомендации — P1

- Синхронизировать решения и вкус между устройствами, восстановить их при переустановке. Сейчас отказ от повторов опирается на локальные решения.
- Повторять серверные записи signals/attendance через надёжную очередь: сейчас часть этих записей выполняется без обработки результата.
- Дедупликация одного мероприятия из разных источников по месту, времени, организатору и названию; нормализовать категории и цены.
- Учитывать доступность по времени, расстояние, бюджет, актуальность, отмены и явный отказ. Ограничить повторение автора/площадки и похожих событий.
- Добавить явные «Не интересует», «Далеко», «Дорого» и изменение интересов. Не скрывать управление вкусом за панелью разработчика.
- Измерять долю повторов, разнообразие, открытия, сохранения и реальные посещения. Сравнить базовый алгоритм и новую версию на одинаковом наборе данных.

Готово, когда: просмотренные карточки не возвращаются самопроизвольно ни на втором телефоне, ни после переустановки; качество оценивается по данным, а не по сложности алгоритма.

### 4. Карта Алматы — P1, затем P2

Уже добавленные объёмные контуры используют действующий Mapbox Streets. Это первый 3D-слой. Рельеф Copernicus, Overture и государственный реестр ещё не импортированы. Полные модели гостиницы «Казахстан»/Esentai — следующий самостоятельный слой.

Для ИИ с доступом к источникам, серверу и хранилищу подготовлен [отдельный промпт по импорту и интеграции карты](MAP-DATA-PROMPT-2026-10-20.md). Он содержит все восемь присланных ссылок, этапы регионального пилота, контракты тайлов, проверки и требования к отчёту; Threads используется как референс идей и дизайна.

| Источник | Для чего нужен | Обработка и ограничения |
|---|---|---|
| [OpenStreetMap](https://www.openstreetmap.org/copyright) | Дороги, здания, адреса, входы, дорожки | Региональная выгрузка → проверка геометрии → PostGIS/тайлы; ODbL и атрибуция |
| [OpenMapTiles](https://openmaptiles.org/) | Схема векторных тайлов | Это схема и инструменты, не готовые свежие данные обо всём Казахстане; отдельно проверить лицензии выбранного стиля и ПО |
| Overture buildings | Дополнительные контуры и атрибуты зданий | Загружать регион и конкретный выпуск; сопоставлять с OSM, не рисовать дубли; лицензия зависит от набора и источника |
| [Overture places](https://docs.overturemaps.org/guides/places/) | Организации и места | Нормализация категорий, названий RU/KZ, происхождение и дата обновления; правила [атрибуции](https://docs.overturemaps.org/attribution/) проверить для конкретного выпуска |
| [Copernicus DEM](https://registry.opendata.aws/copernicus-dem/) | Рельеф, высота маршрута, горы | Геопривязка/мозаика → DEM-тайлы → CDN. Это поверхность местности, не точные индивидуальные 3D-модели зданий |
| [Реестр eGov](https://data.egov.kz/datasets/view?index=s_buildings) | Официальные адреса и идентификаторы | Проверить реальные поля, покрытие и условия доступа. Без координат — адрес помечать приблизительным, хранить метод и уверенность |
| Собственные GLB-модели | Узнаваемые здания, фасады, крыши | Получить права на модели/снимки, облегчить меши и текстуры, несколько уровней детализации; грузить только в зоне камеры |

Условия лицензий в этой таблице — исходная схема интеграции, не результат проверки недоступных сейчас страниц. Не объединять базы с разными условиями без сохранения происхождения. Экран «О карте и данных» должен перечислять реально включённые источники и их атрибуцию.

Конвейер: региональный снимок → staging-таблицы PostGIS → валидация и дедупликация → версионированные векторные/DEM-тайлы → CDN → небольшой локальный кэш. Полный GeoJSON города на телефон не отправлять. Для каждого импорта хранить source, source_id, release, licence, updated_at, accuracy и отчёт изменений. Новую версию публиковать атомарно, сохраняя предыдущую для отката.

- Начать с Алматы; районный пилот и проверка точности на известных адресах. Затем расширение, когда готовы стоимость хранения/CDN и процесс обновления.
- Здания показывать при приближении; модели достопримечательностей — ещё ближе. Уменьшать детализацию во время жеста и в энергосбережении.
- Разделить рендер карты и React-пины, перевести массовые точки в слои движка, кластеризовать. Обрабатывать потерю GPU-контекста и недоступные тайлы.
- Для независимых открытых тайлов отдельно выбрать поставщика или собственный MapLibre-конвейер. Добавление источников не означает автоматическую замену Mapbox.
- Симуляцию пробок из поста использовать только как исследовательский прототип. Для реального ETA нужны проверенные дорожные данные и измерение ошибки на поездках; синтетический прогноз не выдавать за наблюдаемые пробки.

Готово, когда: карту можно вращать и приближать без блокировки UI; OSM/Overture не дают двойных зданий; примерные адреса видимо помечены; модели имеют управляемую загрузку; при отказе источника остаётся понятное рабочее состояние.

### 5. Дизайн — P1/P2

Из присланных изображений: светлая геометрия Mapper, плавающий ввод Gemini, спокойный ритм переписки и тонкие стеклянные края. Из тёмного финансового интерфейса — глубина карточек и сдержанный цвет, без постоянных тяжёлых бликов.

- Сохранить собственный тёплый акцент «Рядом» и читаемые шрифты; привести отступы, радиусы, тени, иконки и состояния к единой системе.
- Нижняя панель: плавающая капсула, safe area, тонкий кант, понятное выделение вкладки, доступные подписи и короткий тактильный отклик. Android — плотная поверхность; размытие использовать выборочно.
- Карта: компактная верхняя группа поиска/города/фильтров, независимая кнопка 2D/3D, одна основная карточка места; подписи и атрибуция остаются читаемыми.
- Чат: плавающий ввод, корректный подъём с клавиатурой, спокойные пузыри, даты, очередь и прогресс вложений. Проверить длинные сообщения, ссылки, большой шрифт и узкий экран.
- Профиль: вместо тяжёлой прямоугольной рамки — лёгкий контур аватара/скруглённого медальона с небольшим знаком достижения. Наградные варианты: базовый, металлический, редкий; геометрия, а не постоянная анимация.
- Перчатки и остальные стикеры: единый силуэт, объём, тень и хороший вид на 48/96/192 px. Исходник реакции «БОКС!» и звук punch.wav найдены в точном слиянии; обновлять весь комплект согласованно.
- Системные настройки уменьшения движения и прозрачности, контраст, VoiceOver/TalkBack, области нажатия минимум 44 pt.

Figma подключена в аккаунте на скриншоте пользователя, но её MCP-инструментов и навыков в текущей сессии нет. Создание или изменение Figma-файла здесь не выполнялось. Превью проекта можно подготовить локально; перенос в Figma — после появления инструментов и доступа к нужному файлу.

### 6. Производительность, нагрузка и выпуск

Java не ускорит автоматически React Native-приложение. Карта, камера, анимации и декодеры уже используют нативные компоненты. Сначала профилирование в release-сборке; отдельный модуль Android разумнее писать на Kotlin только для измеренного узкого места. Для iOS нужен отдельный путь, переписывание всего UI удвоит работу.

| Область | Проверка перед выпуском |
|---|---|
| Связь | Нет сети при старте, обрыв после запроса, 500/401/403/429, медленная сеть, смена сети, восстановление после сна |
| Друзья | Встречные заявки, повторный тап, принятие на другом телефоне, удаление и повторное добавление, блокировка |
| Чаты | Последние/старые сообщения, потерянный ACK, очередь после перезапуска, истёкшая ссылка, удалённый собеседник, приватный чат |
| Лента | Исчерпание, отмена, ручной повтор, истечение события во время просмотра, дубли разных источников, второй аккаунт |
| Карта | Длинный жест, 2D/3D, густые пины, потеря сети, возврат из фона, энергосбережение, низкая память |
| Медиа | 10 фото, большой ролик, вертикальная ориентация, HEIC, отказ разрешения, звонок, мало места, повреждённый файл |
| Интерфейс | Клавиатура, safe area, 360 px, увеличение шрифта, скринридер, тёмная тема, отмена жеста |
| База | RLS двумя и третьим аккаунтом, индексы и EXPLAIN ANALYZE на реалистичных объёмах, восстановление бэкапа |
| Нагрузка | Ступени 50/200/1000 активных клиентов на стенде с фиксированным сценарием, метрики p50/p95, ошибки, соединения и стоимость |

Цели для измерения, не обещанные результаты: нативная карта около 60 кадров/с на среднем устройстве, 30 в экономии; минимальный рост памяти после 20 минут чата; отсутствие необъяснимых вылетов в длительном прогоне. Нужны release-профайлы Android и iPhone. Программный WebGL в Chromium не измеряет реальную плавность телефона.

Выпуск: отдельный стенд → тесты и миграция → два телефона → сборка с номером коммита → ограниченное обновление → проверка ошибок/задержек → расширение. Для отката держать предыдущую сборку и совместимую схему. Добавить сбор сбоев и зависаний с удалением чувствительных данных из журналов.

## Что нужно от владельца

Для части с базой по просьбе владельца подготовлен [готовый промпт другой ИИ с SQL](BACKEND-PROMPT-2026-10-20.md). Его можно передать целиком; прямой доступ к базе этой сессии для передачи задания не нужен.

1. Точная ветка с перчатками и рамкой найдена: `ccr-9e0d2f98-tjjf3m`, `1701723`. При проверке на телефоне сверить именно номер установленной сборки.
2. В настройках облачного окружения разрешить Supabase, Mapbox и нужные источники данных. Сейчас HTTPS-запросы к присланным страницам и Management API отвечают запретом сетевого прокси. Настройки среды не описывают состояние интернета на телефоне.
3. Подключить доступ к тестовому Supabase через защищённые настройки окружения. Секреты, пароли и коды входа в чат не присылать. Сейчас секретов и учётных записей сервиса в окружении нет.
4. Сначала проверить наличие миграции **27**; если её нет — применить `20261012000027_phone_feedback.sql` на стенде и затем в проекте. После неё — новую миграцию через SQL Editor или `npm run db:migrate -- 20261020000024`. Затем собрать приложение заново: добавлен нативный модуль обработки изображений, старый бинарник может быть несовместим с OTA-обновлением.
5. Для финальной проверки — два тестовых аккаунта и реальные телефоны. Нужны сведения о моделях, ОС и версии приложения; коды входа остаются у владельца.
6. Для Figma — сделать инструменты доступными именно этой сессии и указать файл/проект. Повторная установка по скриншоту не требуется.

## Проверки в репозитории

`npm run typecheck`, `EXPO_NO_TELEMETRY=1 npm run lint`, `npm test -- --runInBand`, `npm run test:db`, `npm run build:web`.

`test:db` запускает отдельный PostgreSQL WASM с реальными исходными таблицами/политиками друзей и сокращённой схемой чатов. Проверяет новую миграцию дважды, права заявок, дружбу, блокировку, повторную отправку и запрет изменения чужого сообщения. Это не полная реплика Supabase и не проверка работающей базы. Результаты последнего прогона и изображения — в `docs/progress/quality-oct20/`.
