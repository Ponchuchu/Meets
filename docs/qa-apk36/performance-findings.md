# Meets: разбор производительности и план восстановления

Состояние отчёта: базовый прогон APK 35; APK 36 ещё не измерен. Исходный код: `codex/apk35-media-performance`, `56c79b9`. Никакие исправления в исходниках в рамках этого аудита пока не внесены.

## Условия и границы вывода

- Эмулятор `ryadom_pixel`, `emulator-5554`, Android 15, 1080×2400, 60 Гц, 4 ГБ памяти, 6 виртуальных CPU.
- Опубликованные APK содержат ARM64. Выполнение идёт через ARM-трансляцию на x86_64. Для запуска оригинального APK его неизменённые `.so` извлечены в каталог нативных библиотек приложения.
- GPU `host` сначала заблокировался в графическом аллокаторе; дальнейшие измерения сделаны после холодного запуска AVD с `swiftshader`. Это данные эмулятора с программным рендером, не оценка FPS физического телефона.
- Первые открытия содержат JIT, загрузку изображений и создание карт. Их нельзя напрямую сравнивать с прогретым запуском другой версии.
- HWUI framestats измеряет окно Android. Mapbox и видео имеют отдельные поверхности; число HWUI-кадров не является полным FPS карты/видео.
- В `framestats` p95 гистограммы охватывает все кадры после reset; CSV хранит ограниченный хвост. Например, у рекомендаций CSV содержит 120 из 259 кадров, поэтому percentile этих двух источников расходится закономерно.
- `apk35-reco-warm` исключён: ноль отрисованных кадров, интерфейс остался в иной сцене. Значение p95=4950 в пустой гистограмме не является замером задержки.
- Старые `logcat.txt` содержат хвост предыдущих сцен; предупреждения нужно привязывать к временному окну трассы. Новые прогоны должны писать отдельный поток logcat на время сценария.

## Полученные измерения APK 35

Сценарии по 20 секунд. Все пять содержат непустые Perfetto-трассы, framestats, память до/после и logcat.

| Сценарий | HWUI кадры / janky | HWUI p50 / p95, мс | PSS до → после, МиБ | Что проверялось |
|---|---:|---:|---:|---|
| Карта | 69 / 69 | 46 / 57 | 568,6 → 580,3 | Перемещения камеры |
| Рекомендации | 259 / 259 | 113 / 300 | 364,5 → 487,4 | Восемь отправленных свайпов; включает холодную загрузку |
| Открыть / вернуть | 80 / 79 | 150 / 900 | 484,7 → 624,4 | Три открытия и возврата |
| Галерея | 15 / 13 | 121 / 700 | 713,1 → 768,4 | Горизонтальные жесты у события с тремя фото |

В APK 35 галерея и воспроизведение сохранённого видео не реализованы. Последние две строки описывают попытку выполнить сценарий, а не успешное листание/воспроизведение. PSS после одного короткого прогона не доказывает утечку: здесь смешаны кэши, JIT, карты и декодирование изображений.

## Что видно в CPU-профиле

`work/analysis-agent.py` потоково читает `process_tree` и `compact_sched` из исходной трассы, пропуская тяжёлые print-события. Результаты находятся в `cpu-summary.json` рядом с каждой трассой. Потерянных ftrace-бандлов не отмечено; учёт CPU исключает незавершённые края интервала.

| Сценарий | Главные потребители CPU за ~19–20 секунд |
|---|---|
| Карта | MapboxRenderThread 9366 мс; RenderThread 2758 мс; main 2486 мс; JS 510 мс |
| Рекомендации | RenderThread 16507 мс; JS 4715 мс; main 4438 мс |
| Открыть / вернуть | RenderThread 7191 мс; main 4555 мс; JS 2554 мс; три разных MapboxRenderThread суммарно 5696 мс |
| Галерея | main 1793 мс; JS 1091 мс; MapboxRenderThread 727 мс суммарно; RenderThread 558 мс |
| Видео | RenderThread 3106 мс; MapboxRenderThread 1442 мс суммарно; main 1098 мс; JS 230 мс |

Следствие: для карты в этом запуске основная нагрузка — нативный рендер, а не вычисление рекомендаций в JS. Для свайпов большая доля времени у RenderThread; программный рендер и ARM-трансляция усиливают этот эффект. Три разных render-thread ID при трёх открытиях согласуются с повторным созданием мини-карт. Это не доказательство одновременной работы трёх карт.

Существующий разбор atrace также показывает `MountItemDispatcher::mountViews` до ~1296 мс при открытии, `decodeBitmap` до ~415 мс при рекомендациях и длинные интервалы JIT. Длительность atrace-среза включает ожидание и вытеснение; её нельзя называть чистым временем CPU.

## Что нельзя объявлять подтверждённым

- Нет доказательства двойного декодера из копии FeedCard в переходе: `EventFeedCard` имеет `active=false` по умолчанию, поэтому копия без active не запускает видео.
- Нет доказанной утечки памяти по одному приросту PSS.
- Нет замера 90/120 FPS: дисплей эмулятора работает на 60 Гц.
- Показатель 100% janky в программном эмуляторе не означает 100% janky на телефоне.
- Наличие тестов и успешной web-сборки не подтверждает нативное декодирование/жесты Android.

## Обновление после официального APK36

Матрица36 собрана до изменений исходников. Числа всех прогонов и исключения — в `comparison-metrics.json`. Для ориентира: карта35 warm HWUI p95 57 мс / PSS 573→582 МиБ, карта36 61 мс / 603→583 МиБ; открытие/возврат35 p95 900 мс / 485→624 МиБ,36 1100 мс / 437→654 МиБ. Это разные разведочные проходы на программном эмуляторе, недостаточные для вывода о статистическом ухудшении или ускорении. В галерее и видео36 выполняет работу, которой35 ещё не делала.

P02/P04/P05 исправлены в исходниках: общая композиция Hero/EventFacts, императивная пауза нативного видео при blur/background, прямой рендер одиночного медиа. P04 пока подтверждён тестом жизненного цикла и анализом freeze, а не наблюдением утечки декодера. P03: в36 уже есть `nearMap` и отложенный LiveMini; переносить предложение из отчёта35 как новое реализованное исправление нельзя. P06 остаётся неподтверждённой утечкой — одного роста PSS недостаточно.

Локальная release-сборка остановлена Device Guard на hermesc.exe после создания JS bundle. Защита Windows не изменялась. Обычный debug APK готовится для функциональной проверки, но его CPU/framestats не будут выдаваться за сравнимый release-бенчмарк. Для доказательства ускорения исправлений требуется новый release APK и повтор без параллельной сборки на ПК.
